# DK-ACC-006 / DK-ACC-007 — Immutable validated bookkeeping

## Requirement

Users must not be able to alter, backdate or delete a finally posted transaction.

## Product control

Dolibarr DK uses two layers:

1. PHP `PostingGuard` / Dolibarr bookkeeping triggers.
2. MariaDB BEFORE UPDATE / BEFORE DELETE triggers as final integrity boundary.

The DB guard is installed by `DkDatabaseGuardInstaller` during DK module activation.

## Protected state

A bookkeeping row is considered final when `date_validated IS NOT NULL`.

Once final, all bookkeeping content fields are immutable, including:

- transaction/piece identity,
- document date/reference/type,
- account/subledger,
- debit/credit/amount,
- currency data,
- journal,
- actor/creation data,
- matching/lettering,
- validation timestamp.

`date_export` and automatic `tms` are classified as operational metadata and may change without altering the posted transaction.

## Test evidence

Test IDs:

- CT-ACC-006
- CT-ACC-007

Automated test:

`tests/integration/test-bookkeeping-immutability.sh`

Reference runtime:

- Dolibarr 24.0.0 official Docker image (PHP 8.2)
- MariaDB 11.4

The test connects directly as MariaDB root after installing the guard and verifies:

- unvalidated amount can be corrected;
- NULL -> non-NULL validation is allowed;
- amount update after validation fails;
- backdating after validation fails;
- account change after validation fails;
- lettering change after validation fails;
- validation cannot be cleared;
- validated row deletion fails;
- export timestamp update succeeds.

Because the mutation attempts are executed directly in SQL, this evidence also covers application-trigger bypass and Dolibarr `$notrigger=1` paths.

## Residual assumptions

- production DB administrative access is restricted by the managed-cloud security profile;
- DB triggers are monitored as a required compliance control;
- each supported Dolibarr upgrade passes the accounting schema/write-path compatibility gate.
